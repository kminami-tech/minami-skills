# クラウドや外部サービスを使う学習

外部サービスを使う学習には、ローカルだけの学習にはない危険が 3 つある。お金がかかること、意図せず公開されること、別のアカウント(本番など)を操作してしまうこと。ドキュメントで先回りして防ぐ。

## 事前準備のドキュメントに入れること

- **アカウントの確認:** 操作前に「誰として、どのアカウントで」ログインしているかを確かめるコマンド(AWS なら `aws sts get-caller-identity`)。本番用らしいプロファイルが見つかったら、学習用を使うよう注意書きを入れる
- **リージョンや提供範囲:** 新しいサービスは使えるリージョンが限られることがある。公式の発表やドキュメントで確かめる
- **ツールのバージョン:** 新しいサービスのコマンドは古い CLI にないことがある。バージョン確認と更新手順を入れる
- **ログイン方法:** 長期のアクセスキーより、短時間で期限が切れる認証(AWS なら `aws sso login` や `aws login`)を勧める

## リソースを作るステップに入れること

- **作られるものの一覧:** リソースの種類・名前・役割を表にする。後片付けの手順はこの表から作る
- **課金の始まり:** 「このステップから課金対象になる」と冒頭に書く
- **公開範囲:** 既定で公開になる設定(公開 URL、公開バケットなど)は、そのステップでユーザーに選んでもらう。公開にする場合は、学習後すぐ削除することを明記する
- **費用の上限:** 同時実行数やスケールの上限など、想定外の費用を防ぐ設定があれば勧める(値の範囲は必ず確かめる)
- **「成功」と「動いている」の区別:** デプロイ成功の表示とアプリが動いていることは別。実際にアクセスして確かめる手順と、失敗したときに見るログの場所を書く

## 後片付けのドキュメント

- 作成と逆の順に消す。依存関係(ポリシーを外してからロールを消す、中身を空にしてからバケットを消す、など)を手順に反映する
- 自動で作られて残りやすいもの(ログ、コードの保存先、実行ロールなど)を忘れない。サービスを消しても残るものがないか、ドキュメントで確かめる
- 共有されるリソース(複数の関数が使うバケットなど)は、ほかに使っているものがないか確かめてから消す
- バージョニングが有効な保存先は、通常の削除では古いバージョンが残ることがある
- 最後に「全部消えたこと」を確かめるコマンドと、期待する結果の表を載せる
- 手元に残る変更(設定ファイル、ドキュメント)の一覧を載せ、コミットするかはユーザーに任せる
