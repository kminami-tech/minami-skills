# 確かめ方

学習用ドキュメントの誤りは、学習者がそのまま実行して失敗する形で表に出る。しかも学習者は、誤りがドキュメント側にあるとは気づきにくい。だから書く前に確かめる。

## 根拠にするものの優先順位

1. **手元にインストールされているツールのヘルプ**(`<cmd> --help`、`aws <service> <op> help` など)
   ユーザーが実際に使うバージョンの仕様なので、最も確実。オプション名、値の範囲、既定値はここで確かめる
2. **インストール済みパッケージのソースや同梱ドキュメント**(`node_modules/<pkg>/`、`site-packages/` など)
   既定値や内部の動き(いつファイルを読み込むか、どの環境変数を見るか)を確かめられる。ファイルパスと行番号を根拠として示す
3. **公式ドキュメント**(ドキュメント検索の MCP があれば使う)
   新しい機能は学習データより新しいことが多いので、記憶に頼らず検索する
4. **公式ブログや信頼できる記事**
   補足として使う。1〜3 と食い違ったら 1〜3 を優先する

## 特に確かめるべきもの

- オプションや設定値の **範囲**(最小値・最大値)と **既定値**
- 自動で作られるものの **名前** と **中身**(既定のリソース名、自動生成されるファイル)
- コマンドが **何を作り、何を消すか**(削除コマンドが関連リソースもまとめて消すか、など)
- ツールの **バージョン要件**(新しいコマンドが古い CLI にない、など)

## 確かめられなかったとき

- 「未確認」と明記し、ユーザーが確かめる方法(コマンドや見るべき出力)を添える
- 推測で書く場合は、何を根拠にした推測かを書く(例: 「ヘルプの `--force-include` の説明から、シンボリックリンクを除外している可能性が高い」)
- 試せば分かることなら、「試して、こうなったらこう直す」という形にする

## 誤りが分かったとき

- 誤りを認め、正しい値と根拠を示す
- ドキュメントを直す。似た値を確かめずに書いた箇所がほかにないかも見直す
- 「何も作られていないはず」のように、確かめていない安心材料を言わない。確かめる方法を示す
