# PR の説明文を書く

## 概要

ベースブランチとの差分を読み、レビュワーが何を見ればよいか分かる PR 説明文を組み立てて提示する。

**このスキルは本文を作るところまでを担う。`gh pr create` は実行しない。**
PR を出すかどうかは、本文を見た人間が決める。

読み手はレビュワーである。**レビュワーが知りたいのは「何が変わったか」ではなく「どこを疑って読むべきか」。**

## 使う場面

- `gh pr create` を実行しようとしている
- PR の説明文やタイトルを書く、書き直す
- レビューを依頼する
- 「PRの説明を書いて」と頼まれた

使わない場面: コミットメッセージ（`writing-conventional-commits` を使う）、リリースノートの生成、Issue の起票。

## 手順

### 1. ベースブランチを確定する

```bash
gh repo view --json defaultBranchRef --jq .defaultBranchRef.name
git rev-parse --abbrev-ref HEAD
```

`gh` が使えない場合は `git symbolic-ref refs/remotes/origin/HEAD` で代替する。
どちらも取れないなら、ベースブランチを推測せず聞く。

### 2. 差分を読む

```bash
git log --oneline <base>..HEAD
git diff <base>...HEAD --stat
git diff <base>...HEAD          # 主要ファイル
```

3つのドット `...` を使う。ベースブランチが進んでいても、このブランチの変更だけを見られる。

**コミットメッセージだけを読んで本文を書いてはいけない。** diff を読む。
diff が大きくて全部読めない場合は `--stat` で当たりをつけ、変更行数の多いファイルと設定・スキーマ・公開APIに関わるファイルを優先して読む。読めなかった範囲があるなら、その事実を本文と一緒に伝える。

### 3. テンプレートを探す

```bash
ls .github/PULL_REQUEST_TEMPLATE.md .github/pull_request_template.md docs/PULL_REQUEST_TEMPLATE.md 2>/dev/null
```

**テンプレートがあれば、その項目立てに従う。項目を無言で削らない。**
埋められない項目は、消さずに「未確認」「該当なし」と理由付きで書く。

### 4. 本文を組む（テンプレートが無い場合）

**タイトル**: コミットメッセージと同じ形式。`<type>(<scope>): <説明>`、説明は日本語、句点なし。

```markdown
## なぜ

<解決したい課題と背景。この PR が無かったら何が困るのか>

## 変更内容

**判断が必要な変更**
- <レビュワーに読んでほしい変更。設計判断を含むもの>

**機械的な変更**
- <一括置換、依存更新、フォーマットなど、流し読みでよいもの>

## 動作確認

<実際に実行したコマンドと結果。未実施のものは「未確認」と書く>

## 見てほしい点

- <判断に迷った箇所、捨てた代替案とその理由>

## 関連

Refs #123
```

「判断が必要な変更」と「機械的な変更」の分離は、レビュワーの時間配分を決めるためのもの。
どちらか一方しかない場合は、片方の見出しを省いてよい。

### 5. 提示する

本文を ``` で囲んで示し、そのまま使えるコマンドを添える。

```bash
gh pr create --base <base> --title "<タイトル>" --body-file <ファイル>
```

## 例

```markdown
## なぜ

アクセストークンの有効期限が15分と短く、長時間の操作中にセッションが切れる
報告が3件あった。#421

## 変更内容

**判断が必要な変更**
- 401 を受けたときにリフレッシュを1回だけ試み、失敗したらログアウトさせる
  （無限リトライを避けるため試行回数を1回に固定した）
- リフレッシュ中に発生した並行リクエストは待たせて、同じトークンを共有する

**機械的な変更**
- `apiClient` の呼び出し 14 箇所を新しいラッパー経由に置換

## 動作確認

- `npm test` — 全件通過（新規テスト12件を含む）
- ローカルで有効期限を30秒に短縮し、期限切れをまたぐ操作が継続することを確認
- 未確認: リフレッシュトークン自体が失効した場合の挙動（検証環境で再現できず）

## 見てほしい点

- 並行リクエストの待たせ方に Promise の共有を使っています。ここは
  ミューテックスを入れる案も考えましたが、単一の Promise で足りると判断しました
- リトライ1回という上限が妥当か

## 関連

Closes #421
```

## よくある失敗

| 失敗 | どうするか |
|---|---|
| コミットメッセージを箇条書きで並べただけ | `git log` はレビュワーが自分で見られる。PR本文は目的単位で書く |
| 確認していないのに「動作確認済み」と書く | 根拠は実際に実行したコマンドと出力のみ。未実施は「未確認」と書く |
| 「見てほしい点: 特になし」で埋める | 本当に無いなら、なぜ無いのか（機械的変更のみ、等）を書く |
| diff を読まずコミットメッセージから書く | `git diff <base>...HEAD` を読む。例外なし |
| テンプレートの項目を黙って削る | 残して「未確認」「該当なし」と理由付きで書く |
| 「なぜ」に変更内容を書いてしまう | 「なぜ」は変更前の困りごと。変更内容は次の節に書く |
| `..`（2ドット）で diff を取る | `...`（3ドット）を使う。ベース側の進行を差分に混ぜない |
| 変更行数を誇るような書き方 | 行数はレビュワーの判断材料にならない |

## PR が大きすぎるとき

diff が数百行を超え、目的が2つ以上含まれている場合、**1本の説明に丸めない。**

1. 目的ごとに変更をグループ分けして示す
2. 分割した場合の PR の順序と依存関係を示す
3. 分割せず1本で出す判断なら、それに従う。ただし本文の「変更内容」を目的ごとの見出しに分け、レビュワーが分割して読めるようにする

## レビュー依頼の一言

本文とは別に、依頼メッセージを添える場合。

- レビューしてほしい観点を1つに絞って伝える（設計の妥当性か、実装の正しさか、影響範囲か）
- 急ぎかどうか、いつまでに必要かを書く
- 「お手隙のときに」で締めるより、期限を書いた方がレビュワーは動きやすい
